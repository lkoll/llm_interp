Append-only log of design choices not fully specified in `project_outline.md`, in the order they were made. Each entry: date, decision, why.

## 2026-10-15 — Package layout

Src-layout: `src/llm_interp/` as the installable package (hatchling build backend), with subpackages `config/`, `adapters/`, `generate/`, `prompts/`, `store/`, `validate/` matching the outline's module list; `hooks.py`, `capture.py`, `recompute.py`, `loader.py`, `cli.py` live as flat modules directly under `src/llm_interp/` (added as each build step is implemented, not pre-created as empty stubs). `configs/` (YAML run configs) and `tests/{unit,integration}/` sit at the repo root, not inside the package. Chosen for standard, uv-friendly packaging and clean `pytest`/CLI imports; not specified explicitly in the brief.

## 2026-10-15 — Python interpreter

`requires-python = ">=3.12,<3.13"`, pinned via `.python-version` to a uv-managed CPython 3.12.15 (not the system Python, which is 3.14). Narrowed from the initially-planned `>=3.11` after `zarr==3.4.1` turned out to require Python >=3.12 — still within CLAUDE.md's "let uv manage a 3.11/3.12 interpreter."

## 2026-10-15 — RunConfig shape

`RunConfig` (`src/llm_interp/config/schema.py`) groups fields into `model` / `capture` / `generation` plus top-level `run_name` and `storage_root`, matching the brief's listed fields (model id+revision, dtype, device, attention impl, layers/sites, storage root, generation params) one-for-one. All four pydantic models are frozen.

- `capture` doesn't carry a generic `sites: list[str]`. The outline's actual capture semantics (step 5) are: resid_pre for the configured `layers`, the final residual, and top-k logprobs, always; post-QK-norm pre-RoPE q/k only for validation runs. Modeled that directly as `layers: list[int]`, `capture_final_residual: bool`, `top_k_logprobs: int`, `capture_qk_pre_rope: bool` rather than inventing a generic site-name list — avoids a layer of indirection nothing downstream needs yet.
- `layers` validation (non-negative, no duplicates, sorted) happens at the schema level; validation that the layer indices are in-range for the actual model (0-27 for the 0.6B, 0-35 for the 8B) is deferred to the adapter once the model config is loaded, per the outline's "read all dims from config" principle — `RunConfig` itself has no model-specific knowledge.
- `generation.max_new_tokens` set to 768 in both configs — not specified in the brief beyond "cap it, 0.6B rambles." A judgment-call default, not validated against actual generation behavior yet; revisit once `estimate`/`generate` exist and real trace lengths are visible.
- Pinned `Qwen/Qwen3-8B` to commit `b968826d9c46dd6066d109eabc6255188de91218` for the (unrun) cloud config, with the same due diligence as the 0.6B pin — fetched `config.json` at that commit and confirmed 36 layers, 32 attention heads, 8 KV heads, head_dim 128, matching the outline.

## 2026-10-15 — ArchAdapter interface and Qwen3Adapter

Read the installed `transformers==5.19.0` source (`transformers/models/qwen3/modeling_qwen3.py` and `configuration_qwen3.py`) directly rather than assuming module names. Confirmed: `model.model.embed_tokens`, `model.model.layers[l]` (resid_pre[l] hook target), `.input_layernorm`, `.self_attn.{q,k,v}_proj`, `.self_attn.{q,k}_norm` (per-head RMSNorm, applied post-reshape pre-RoPE), one shared `model.model.rotary_emb` across all layers, `model.model.norm` (final norm), `model.lm_head`. Per-layer attention type comes from `config.layer_types[layer_idx]` (all `"full_attention"` for Qwen3 — no sliding window).

- `ArchAdapter` (`src/llm_interp/adapters/base.py`) exposes dims as properties (all read from `model.config`, nothing hardcoded) plus one method per logical site, typed to return `nn.Module | None` so a future adapter (Gemma 3, Qwen3.6) can report an absent site. Three recompute primitives live on the adapter rather than in a generic `recompute.py` function table: `reshape_to_heads` (generic default, overridable), `apply_qk_norm` and `apply_rotary` (both abstract — architecture-specific). `recompute.py` (0.4) will orchestrate these plus the GQA repeat and causal-mask attention-score math, which is *not* architecture-specific and doesn't belong on the adapter.
- `apply_rotary` calls the real `apply_rotary_pos_emb` function imported from `modeling_qwen3`, not a reimplementation — guarantees bit-exact RoPE application without duplicating the rotate-half math.
- Verified adapter correctness against the real model, not just shape: `tests/unit/test_adapters.py::test_apply_qk_norm_and_rotary_match_real_forward` monkeypatches the module-level `apply_rotary_pos_emb` during a real forward pass to capture its pre/post-rotary tensors as ground truth (there's no other hook point for that intermediate value), and asserts the adapter's `reshape_to_heads -> apply_qk_norm -> apply_rotary` chain reproduces it bit-for-bit. This is effectively check (c) run early, at the adapter level.
- Tiny random-init Qwen3 fixture (`tests/unit/conftest.py`) deliberately sets `head_dim=16` while `hidden_size=32, num_attention_heads=4` (so `hidden_size // num_attention_heads == 8 != 16`), to exercise the head_dim-!=-hidden/heads gotcha on every adapter test, not just the real 0.6B model.

## 2026-10-15 — HookManager

`HookManager` (`src/llm_interp/hooks.py`) is a single class handling both capture and the add-vector primitive, per the outline's "one hook manager handles both reading and writing." Internally it's built on one generic mechanism — a dict of `key -> nn.Module` capture targets and `key -> (nn.Module, vector)` add-vector targets, both realized as `register_forward_pre_hook(..., with_kwargs=True)` on `__enter__` and always removed on `__exit__` (return `False`, never swallow the exception). `capture_resid_pre(layers)` is the only public capture method for now (matches the 0.3 scope); it populates that same internal target dict, so a later `capture_final_residual()` (needed by `capture.py` in 0.7, hooking `adapter.final_norm()`) is a thin addition, not a redesign.

- Confirmed empirically (not assumed) that in `transformers==5.19.0`, `Qwen3DecoderLayer.forward`'s `hidden_states` arrives positionally (`args[0]`), not as a kwarg — `Qwen3Model.forward` calls `decoder_layer(hidden_states, attention_mask=..., ...)`. The hook still checks `kwargs` first and falls back to `args[0]`, per the outline's explicit warning that this can vary by version.
- Verified against ground truth independent of the hook mechanism itself: `test_capture_resid_pre_layer0_matches_embeddings` compares the hook's capture to calling `adapter.embeddings()` directly; `test_capture_resid_pre_layer1_matches_layer0_output` compares it to a separate, independent `register_forward_hook` on layer 0 capturing its output.
- `test_captures_are_detached_cloned_cpu` confirms `requires_grad is False`, `device.type == "cpu"`, and `data_ptr() != original.data_ptr()` (a real clone, not an alias) by grabbing the pre-clone tensor via a second, independent hook.
- Add-vector tests are a hook-level preview of validate check (f): zero vector added at a layer leaves logits bit-exact; a nonzero vector changes them. Full check (f) lands in 0.8 against the real model.

## 2026-10-15 — recompute.py and checks a/c (real model); check e deferred to 0.7

`recompute.py` implements the full outline step 7 pipeline now (input norm -> q/k/v proj -> reshape -> QK-norm -> RoPE -> GQA repeat -> scaled causal attention -> final norm -> lm_head), even though only checks (a) and (c) are gated at this step; (b)/(d)/(f) land in 0.8 against the real model, and (e) is deferred — see below.

- `repeat_kv` and the causal-mask attention math are written independently in `recompute.py` rather than imported from `modeling_qwen3`, since the GQA-repeat convention and causal masking are standard across HF attention implementations, not Qwen3-specific — keeping `recompute.py` architecture-agnostic (it only calls into the adapter for anything that could vary, e.g. `attention_scaling`).
- Added `ArchAdapter.attention_scaling(layer_idx)` (reads the real `self_attn.scaling` attribute) rather than hardcoding `head_dim**-0.5` in `recompute.py` — the outline flags Gemma 3's "custom attention scaling" as a reason this must stay adapter-owned, not a generic formula.
- Added `HookManager.capture_final_residual()` (hooks `adapter.final_norm()`), as predicted in the 0.3 entry — needed by check (a).
- **Device handling**: captures live on CPU (CLAUDE.md), but recompute runs the real modules, which may be on GPU. `recompute_qk_pre_rope`, `recompute_v`, and `recompute_logits` each move their input tensor to the target module's device internally (`next(module.parameters()).device`) rather than pushing that responsibility onto every caller — this surfaced as a real bug (device-mismatch `RuntimeError`) the first time checks (a)/(c) ran against the real GPU-resident model, caught immediately rather than silently producing wrong results on CPU-only test runs.
- **Checks (a) and (c) now run against the real Qwen3-0.6B** (`tests/integration/test_checks.py`, `@pytest.mark.gpu`), not just the tiny CPU fixture: check (a) on one real forward pass; check (c) across *all 28 real layers* in a single pass (cheap enough not to sample). Both pass at `atol=rtol=1e-4` (not bit-exact — real GPU kernels for the norm/linear ops don't guarantee bit-identical accumulation order between the model's own forward and a second, separately-dispatched call to the same modules, even in fp32 with deterministic algorithms on). The tiny-fixture CPU previews in `tests/unit/test_recompute.py` *are* bit-exact (`assert_close` default tolerance), since CPU fp32 ops there are deterministic enough end-to-end.
- `pyproject.toml` pytest `addopts = "-m 'not gpu'"`: plain `uv run pytest` now runs only the CPU unit suite (fast, no download); `uv run pytest -m gpu` opts into the real-model integration tests.
- **Check (e) is deliberately not implemented in this step.** `task_list.md` notes it "lands with store" — a bit-exact Zarr/Parquet round trip (fp32 and bf16-as-uint16) needs the actual storage format from 0.7, which doesn't exist yet. Implementing a throwaway standalone round-trip test now (bypassing the real `store/` module) would test the wrong thing and get thrown away; deferred so check (e) exercises the real storage code path once it exists.

## 2026-10-15 — generate/: Generator interface, HFGenerator, render_and_tokenize

Verified the chat-template/thinking-mode behavior empirically against the real tokenizer before writing anything, rather than assuming: with `enable_thinking=True`, Qwen3's template renders `...<|im_start|>assistant\n` and leaves `<think>` for the *model* to generate; `enable_thinking=False` force-inserts an empty `<think>\n\n</think>\n\n` block instead. A real generation with the project's exact sampling config (T=0.6, top_p=0.95, top_k=20, min_p=0) confirmed the expected shape: opens `<think>`, closes `</think>`, emits the requested JSON, stops on `<|im_end|>` (== `eos_token_id` 151645).

- `Generator.generate(input_ids, generation_config)` takes and returns token IDs only, never text — `HFGenerator` doesn't even hold a tokenizer, just the model (reads `eos_token_id`/`pad_token_id` off `model.config`). This is what lets `VLLMGenerator` share the exact same interface later: swapping generators is a config change, not a rewrite of any call site.
- `GenerationResult` stores one `full_ids` tensor (prompt + generated, CPU) plus `prompt_len`, with `generated_ids` as a derived slice property — avoids duplicating the prompt in two fields, consistent with "token IDs are the source of truth."
- **Stop-reason detection** (`eos` vs `max_new_tokens`) is inferred from whether the last generated token is in the model's eos set — correct and sufficient here since generation is single-sequence, sampled (never greedy), with no beam search or custom stopping criteria. Factored into a pure function (`_stop_reason`) specifically so it's unit-testable without relying on a random tiny model happening to emit eos within N steps.
- `render_and_tokenize` (`generate/prompt.py`) implements the brief's invariant exactly: render once (`apply_chat_template(tokenize=False, enable_thinking=...)`), tokenize that text once (`add_special_tokens=False`, `return_offsets_mapping=True` — needed later for hint-span lookup), and raise `ValueError` (not a bare `assert`, which `-O` strips) if it doesn't match `apply_chat_template(tokenize=True)` directly. Bundled the offset mapping into the returned `RenderedPrompt` now even though span-finding is 0.6/0.7's job, since it's produced by the same tokenizer call and would otherwise mean tokenizing the rendered text twice.
- **Real bug caught by testing against the actual tokenizer, not a mock:** `apply_chat_template(tokenize=True, ...)` returns a `BatchEncoding` in this transformers version, which is dict-*like* (has `.keys()`) but is **not** a `dict` subclass — `isinstance(result, dict)` is `False` for it, and naively doing `list(result)` on it (the fallback branch) silently returns its *keys* (`['input_ids', 'attention_mask']`), not the token ids. First attempt at the cross-check assertion passed this bogus list through undetected until a test caught the garbage comparison. Fixed by duck-typing on `hasattr(result, "keys")` instead of `isinstance(..., dict)`.
- `HFGenerator`'s correctness tests (unit, tiny model) check *invariants* (cap respected, stop_reason/truncated agree, same-seed determinism) rather than a specific random outcome, since asserting exactly which branch (eos vs cap) fires on an untrained random model would be flaky. The real-model integration test, by contrast, checks the concrete expected shape (`<think>` before `</think>`, ends on eos or hits the cap) since that behavior is actually determinate for a real instruction-tuned model.

## 2026-10-15 — prompts/: PromptSource, ARC-Easy, JSON parsing, paired-hint generation

Inspected the real `allenai/ai2_arc`/`ARC-Easy` dataset via `datasets` before coding rather than assuming its shape: `{id, question, choices: {text: [...], label: [...]}, answerKey}`. Found a real quirk — a minority of rows use numeric labels (`"1".."4"`) instead of letters, and the number of choices varies (3, 4, or 5), not always 4. `ArcEasyPromptSource` skips numeric-labeled rows (so every hint — "the answer is X" — and every requested `"answer": "C"` refers to a letter consistently) and otherwise accepts any letter-labeled count; selects the first `n` (default 30) from the `test` split in dataset order — deterministic, no shuffling needed since "the results don't matter" (brief).

- **Scope boundary**: this step *does* drive real generation (via 0.5's `Generator`), not just define static data — `task_list.md`'s ordering (0.5 generation -> 0.6 prompts -> 0.7 capture/store) and the brief's "run each with no hint first, then with a hint where X != the model's no-hint answer" make the two-phase generate-then-choose-hint logic intrinsically part of "prompts," not deferred to 0.7. `generate_pair` runs the no-hint condition, picks `hinted_option` from the *actual* parsed no-hint answer (falling back to `!= gold` only when that answer wasn't a valid option — e.g. a parse failure), then runs the hint condition.
- `PairTrace` wraps the lightweight `PairRecord` (the brief's listed fields: pair_id, condition, hinted_option, gold, parsed_answer, plus `parse_status`) together with the `RenderedPrompt` and `GenerationResult` from `generate/` — carries the actual token IDs forward rather than only the decoded summary, since 0.7's capture stage will need them for teacher-forced replay and shouldn't have to regenerate.
- **`parse_answer`** (`prompts/parse.py`) finds the LAST valid JSON object with a string-valued `"answer"` key anywhere in the response text (via `_iter_json_object_spans`, a brace-depth scanner that's string-literal- and escape-aware, catching JSON embedded in reasoning prose or nested one level deep), per `parse_status`: `not_found` (no JSON+`answer` key at all), `malformed` (found one, but the value isn't a non-empty string), `ok` (one distinct string value across every occurrence), `multiple` (the model's JSON disagreed with itself across occurrences — still resolves to the last one, but flagged). Deliberately does *not* validate that the letter is one of the question's actual options, or compute/return a character span for the value — span-to-token mapping is explicitly 0.7's job (CLAUDE.md: map via incrementally decoding stored token-ID prefixes, never by re-parsing text), so adding a span here now would be built against the wrong representation.
- Tested the parser directly against adversarial inputs (reasoning text wrapping the JSON, escaped quotes inside strings, a nested object, invalid `{...}` that isn't real JSON, repeated-same-value vs. repeated-different-value) rather than only the one-shot happy path.

## 2026-10-15 — capture.py and store/: Zarr v3 + Parquet, manifest, check (e)

Verified the exact Zarr v3 API (`create_array`, `.resize()`, attrs, nested group paths, reopening) and the bf16-as-uint16 bit-reinterpretation round trip (`tensor.view(torch.uint16)`) empirically before writing `ZarrStore`, same approach as every prior step — guessing at either would have cascaded into everything downstream.

- **Site arrays are one Zarr array per (site, layer)**, nested by path (`resid_pre/5`, not a single 3D array with a layer dimension) — matches the outline's `resid_pre[l]` notation treating each layer as its own site, and zarr-python v3 auto-creates intermediate groups for `/`-separated `create_array` paths, so this cost nothing extra.
- **One canonical `(start, end)` offset per trace**, read from `positions` (always written, independent of which layers/sites are configured) and asserted equal for every other required site's own `append()` return value. This is a real internal-consistency check, not decoration — if a future change made two sites diverge in token count for the same trace, this catches it immediately instead of silently misaligning the index.
- **Realized-logprob convention**: all per-token sites (`positions`, `top_logprob_values/indices`, `realized_logprob`) are length `N` (the full sequence), not `N-1`, so every site shares the same `(start, end)` range. The last position has no "next token" to score, so its `realized_logprob` is `NaN` — a deliberate, documented sentinel rather than a shorter array that would need its own offset bookkeeping.
- **Primary capture reuses the model's own `out.logits`** from the single teacher-forced forward pass (not `recompute_logits`) — `recompute.py` exists for *validating* that the stored data reproduces the model's computation (checks a/c/d), not for *producing* the stored data; using the model's direct output as the source of truth for top-k logprobs is both simpler and more obviously correct than reconstructing logits a second way just to store them.
- **`spans.py`** is a new top-level module (not inside `store/` or `capture.py`) since it's pure token-ID logic independent of storage format: `find_think_spans` (None if `</think>` never appears — capture.py turns that into the `has_think_close` flag on `traces`, per CLAUDE.md's "flag the trace"), `find_response_span` (extends to sequence end, not an error, if generation was truncated after `</think>` but before eos), `find_hint_span` (via the prompt's real `offset_mapping` — straightforward, since the prompt text is ours), `find_answer_value_span` (the hard one: generated tokens have no offset_mapping, so it incrementally decodes growing token prefixes and matches cumulative character length against the character offset of the parsed answer value — reuses `prompts.parse_answer` rather than re-implementing JSON-finding against the response text a second time).
- **Resumability**: `TraceTables` holds all four tables in memory and rewrites each whole Parquet file on every `flush()` — true incremental Parquet appending isn't natively supported and would add real complexity for no benefit at this toy scale (tens of traces). On load, any `traces`/`spans` row whose `trace_id` isn't in `index` is dropped (an orphan from a crash between flushing those and flushing `index`); `CaptureRunner.run()` separately truncates the Zarr arrays back to `index`'s max `end` before processing anything. Both halves of this were verified against a *simulated crash* (manually appending unindexed garbage to Zarr, then confirming a fresh `CaptureRunner` truncates it away and still captures every real trace exactly once) — not just a conceptual read of the resumability rule.
- **Check (e)** (deferred from 0.4) is now implemented and green: `ZarrStore` round-trips both fp32 and bf16 bit-exact (`torch.equal`, not `assert_close`) as direct unit tests, plus the fp32 path re-verified against real captured activations in the GPU integration test.
- **Position 0 / attention sink**: per CLAUDE.md, "flag it, exclude from stats by default." Not a new stored column — position 0 of every trace is already identifiable directly from the stored `positions` array (`positions == 0`), so there's nothing to add at the storage layer. The actual *exclude from stats by default* behavior belongs to whatever computes statistics over loaded activations — the loader (0.9) and later analysis, not yet built. Flagging this explicitly so it isn't forgotten by the time that code is written.
- `annotations` table exists (schema only, zero rows) per the brief's "reserved for later judgments" — not exercised in Phase 0.

## 2026-10-15 — validate/ checks a-f and doctor CLI

Refactored checks (a) and (c) out of their pytest-only logic (written in 0.4) into real library functions in `validate/checks.py`, so both `doctor` and the tests call one implementation instead of two copies. Built checks (b), (d), (f) fresh and wrapped (e)'s existing `ZarrStore` round trip in a `CheckResult`-returning function too, so `doctor` can run all six in one pass/fail table.

- **Check (d)'s ground truth comes from `output_attentions=True`, not a hook on `self_attn`.** Verified empirically first: passing `output_attentions=True` with `attn_implementation="eager"` returns `out.attentions`, a real per-layer tuple of properly-normalized attention-weight tensors (confirmed `.sum(-1) ≈ 1`). This avoids adding a new `ArchAdapter` method just to expose the raw `self_attn` submodule for hooking — `self_attn` as a whole was never one of the outline's listed logical sites, and `output_attentions` already gives exactly the "attention probabilities" the check needs without reaching past the adapter's interface.
- **Check (b) needed a different tolerance tier than a/c/d/f, discovered by actually running it, not anticipated in advance.** The first run failed on `torch.allclose` with the standard tight fp32 tolerance (`atol=rtol=1e-4`) despite `cosine_similarity ≈ 1.0` and `argmax_agreement == 1.0` — because relative error blows up on near-zero activation components even when the absolute difference is a harmless ~0.005. CLAUDE.md anticipated the *existence* of this gap ("cached decoding and full forward passes legitimately differ") but not the specific failure mode. Fixed by giving check (b) its own gate: an absolute-error-only threshold (`CACHE_VS_TEACHER_FORCED_ATOL`, looser than the standard `TOLERANCES`) plus a minimum cosine similarity, with `max_rel_err` still computed and reported for visibility but not used to decide pass/fail. Checks a/c/d/f keep the tight, dtype-keyed `TOLERANCES` since those compare a recomputation against the *same* forward pass, where true numerical identity is the right expectation.
- Check (b)'s KV-cache replay is a dedicated helper (`_kv_cached_capture`), not `model.generate()`: prefill all but the last 5 tokens in one `use_cache=True` call, then feed the remaining tokens one at a time reusing `past_key_values`, hooking `resid_pre` fresh at each step (`HookManager`'s capture dict is overwrite-once-per-call by design, so each step needs its own `HookManager` instance) and concatenating. Argmax agreement is computed by running `recompute_logits` on the captured `final_residual` from *both* paths — not by comparing generated tokens, which (b) never actually generates.
- `doctor` (`validate/doctor.py`) builds one short fixed validation sentence (no chat template, no real generation needed — these are model/environment mechanics checks, not pipeline checks) and runs all six against a config-loaded model. Only wired up as `uv run python -m llm_interp.validate.doctor [--config PATH]` for now; a unified `llm-interp` CLI entry point dispatching `doctor`/`estimate`/`generate`/`capture`/`inspect` is explicitly 0.9's job — this just needs `run_doctor`/`main` to exist and work standalone so 0.9 can wire them in without rewriting the checks.

## 2026-10-15 — loader, estimate, and the llm-interp CLI

**Real gap found while designing the loader, not anticipated earlier**: nothing in 0.7's `capture.py` ever persisted the actual token IDs — only derived facts (positions, logprobs, spans) were stored. The loader's job ("...returned with decoded tokens") is impossible without them, and per CLAUDE.md token IDs are supposed to be the source of truth anyway. Fixed by adding `token_ids` as a required Zarr site, written alongside `positions` as the two canonical, always-present sites every trace's `(start, end)` offset is checked against (previously only `positions` played that role). This touched 0.7's code and tests, verified against real captured data (`tests/integration/test_capture.py` now asserts the stored `token_ids` round-trip to the exact `full_ids` that were generated).

- `CaptureRunner.run()` now also writes `manifest.json` at the end (previously built by `build_manifest`/`write_manifest` but never actually called from the capture path) — moved into `capture.py` rather than left to the CLI layer, so anyone constructing a `CaptureRunner` directly gets a manifest for free, matching the outline's framing of capture+store as one bundled responsibility.
- **Generation and capture talk through a plain JSON file** (`generated_traces.json`, one per `storage_root`), not a new database — `save_pair_traces`/`load_pair_traces` (`prompts/persist.py`) serialize/deserialize `PairTrace` (token IDs, rendered prompt + offset mapping, generation metadata) so `generate` and `capture` can be genuinely separate CLI invocations, per design principle 3 ("generation and capture... talk only through the trace store"). Not one of the four official Parquet tables; a human-readable intermediate handoff artifact, which is all two sequential CLI steps need.
- `model_loading.py` (new top-level module) extracted the model/tokenizer-loading logic that was duplicated between `doctor.py` and the test `conftest.py`; both now call it. `build_adapter()` hardcodes `Qwen3Adapter` — model-id-based adapter dispatch is a future-adapter (Gemma 3, Qwen3.6) concern, not needed while only one adapter exists.
- `estimate_bytes` fetches the model's `config.json` via `AutoConfig.from_pretrained` — never the weights — so `estimate` stays cheap to run before a potentially very large capture, per the outline's "run before any capture." Running it for real on this project's own 30-pair/60-trace config (`llm-interp estimate`) projects **~5.8 GB** for capturing all 28 layers' resid_pre in fp32 — a genuinely useful number to have before committing to a run, not just a toy example.

## 2026-10-15 — Addendum A, 0.12 Config: MlpCaptureConfig

`dense_layers` and `topk_layers` are two independent lists (both optional, default empty), not a single `mode` enum — the addendum's own cloud default ("topk on all layers plus dense on 4") needs both active simultaneously on overlapping layers, which a single mutually-exclusive mode couldn't express. Overlap between the two lists is explicitly allowed (no validator rejects it) since a layer getting both representations is exactly what the cloud default does.

`CaptureConfig.mlp: MlpCaptureConfig | None = None` — absent by default so the schema stays backward-compatible with the idea of a config that doesn't want MLP capture at all, not just "all neuron capture disabled."

`capture_validation_extras` (dense `mlp_gate`/`mlp_up`/`mlp_out`, for check g only) mirrors the existing `capture_qk_pre_rope` pattern exactly — same "validation runs only" framing, same off-by-default.

**Resolved the "about 25/50/75% depth + last" layer indices** (flagged as open in the task list): 0.6B (28 layers) -> `[7, 14, 21, 27]`; 8B (36 layers) -> `[9, 18, 27, 35]`. Straightforward arithmetic, not worth a separate question.

`numpy` is not yet a direct dependency — `MlpCaptureConfig` itself has no numpy usage; that lands with storage (0.15), which is where `np.packbits` actually gets called.

## 2026-10-15 — Addendum A, 0.13 Adapters: MLP sites

No dedicated `mlp_in` adapter method — it's just the *input* to `mlp(layer_idx)`, and `mlp_out` is that same module's *output*; one module, hooked twice (pre and post), rather than two separate accessors for what's really one site pair. This mirrors how `final_residual` already works (hook `final_norm()`'s input) rather than introducing a new pattern.

`mlp_activation_negative_min` is implemented *once*, concretely, on the `ArchAdapter` base (not abstract, not overridden per adapter) — it's a pure lookup on `config.hidden_act` against a small shared table (`silu`, and `gelu_pytorch_tanh` for a future Gemma 3 adapter), not architecture-specific logic. Only `mlp_activation_fn()` itself stays abstract, since *that* needs a real submodule reference. Raises `NotImplementedError` for an activation not in the table, rather than guessing or silently returning something wrong — verified by constructing a real (tiny) model with `hidden_act="relu"` and checking the raise, not just reasoning about the lookup miss.

`mlp_activation_fn()` returns the model's own already-instantiated `act_fn` object (`ACT2FN[config.hidden_act]`, read off a real `Qwen3MLP`), never a hardcoded `torch.nn.functional.silu` — same principle as `apply_rotary` reusing the model's real `apply_rotary_pos_emb` rather than reimplementing it: guarantees exact match with what the model actually computes, including if a future HF version changes `ACT2FN`'s mapping.

## 2026-10-15 — Addendum A, 0.14 Hooks: MLP sites, output-side captures

`HookManager` previously only captured *inputs* (forward-pre-hooks) — `mlp_gate`/`mlp_up`/`mlp_out` need a module's *output*, which no existing mechanism supported. Added a parallel `_output_capture_targets` dict and a plain `register_forward_hook` path (`_make_output_capture_hook`), alongside the existing pre-hook path, rather than overloading one mechanism to do both — a forward hook's third argument is already the output tensor directly (no args/kwargs ambiguity to resolve the way `_hidden_states_from` has to for inputs).

`mlp_in` and `mlp_act`'s pre-hooks reuse the *existing* `_hidden_states_from` input-extraction helper even though the modules being hooked (`mlp`, `down_proj`) don't have a parameter literally named `hidden_states` — `nn.Linear.forward`'s parameter is `input`. This works because the helper's real logic is "kwarg named hidden_states if present, else first positional arg," and every one of these call sites (`self.mlp(hidden_states)`, `self.down_proj(...)`) is always positional in the actual modeling code — verified directly (`test_capture_mlp_sites_match_real_forward` asserts all five sites, captured in one pass, against independent ground-truth hooks on the real tiny model), not assumed.

Capture key scheme: `(site_name, layer_idx)` tuples (`("mlp_gate", 3)`), distinct from the existing bare-`int`-keyed `resid_pre` captures and the string-keyed `"final_residual"` — avoids any collision risk in the shared `captures` dict now that it holds five new site families.

`test_mlp_act_equals_act_fn_gate_times_up` checks the captured values satisfy `mlp_act == act_fn(mlp_gate) * mlp_up` as a *relationship*, not just that each site was independently captured correctly — this is exactly what check g (0.17) will later verify at scale on the real model; doing it now at the hook level catches a wiring mistake before check g even exists.

## 2026-10-15 — Addendum A, 0.15 Storage: mlp.py codec, capture.py wiring, numpy

`numpy==2.5.4` promoted from transitive to a direct dependency — `mlp.py` calls `np.packbits`/`np.unpackbits` directly for the gate-sign bitmask, exactly the case CLAUDE.md's dependency policy flagged in advance (0.0's entry already called this out before it happened).

Regime computation (`regime_from_signs`) needs only `gate` and `act` — not `up` — since `sign(act) = sign(gate) * sign(up)` already; this is the same fact the addendum uses to justify storing a gate-sign bit instead of both `g` and `u`. Kept as one pure function in a new top-level `mlp.py` (parallel to `spans.py`, `recompute.py`) rather than inside `capture.py` or `store/`, since both `capture.py` (producing) and the eventual check (g) / loader (consuming) need the identical regime logic — a single source of truth for "what a regime code means" was the whole point of having regime codes at all.

`capture.py`'s MLP hook registration always includes `capture_mlp_gate` whenever *any* MLP capture is configured (dense or topk) — gate sign is needed for both dense's packed bits and topk's regime codes — but `capture_mlp_up`/`capture_mlp_out` are registered *only* when `capture_validation_extras` is set. Getting this wrong (e.g. always capturing `up`) would silently blow past the point of the dense/topk space savings the addendum's reference figures are built on.

`dense_layers` and `topk_layers` are allowed to overlap in `_write_mlp_sites` exactly as the config schema allows — a layer in both lists gets both `mlp_act`/`mlp_gate_sign` *and* `mlp_topk_index`/`mlp_topk_value`/`mlp_topk_regime` written, independently, from the same single captured `act`/`gate` pair (no redundant extra forward pass).

Verified against the real model, not just the codec's own unit tests: three GPU integration tests cover dense (bit-exact `mlp_act` and gate-sign bits against independent hooks on a fresh forward pass), topk (shape/dtype/index-range/regime-validity checks), and validation extras (`act_fn(gate) * up == mlp_act` and `down_proj(mlp_act) == mlp_out` — literally check (g)'s first two conditions, previewed here before check g exists as a named check in 0.17).
